# Skills state no API surface

The four skills in `crunes-skills` teach an agent when to reach for a rune, how to read a permission denial, and how to write a rune or a plugin. They deliberately contain **no `@utils` signatures, no namespace lists, no flag tables and no command inventories.**

Everything in that list is generated by the CLI the user actually has installed:

| What an agent needs | Where it comes from |
|---|---|
| Which utils namespaces exist, and their signatures | `crunes docs utils` |
| What a rune's arguments are | `crunes docs rune <key>` |
| What globals the sandbox injects | `crunes docs globals` |
| The whole model, end to end | `crunes docs intro` |
| Which runes this project has | `crunes list` |
| Why a command was refused | `crunes shell explain` |

## Why

**A skill is installed once and read forever; a CLI is upgraded.** A skill that listed the namespaces would have been right on the day it was written and wrong at the next release that added one. The failure is quiet and the worst kind: the agent does not discover a capability it now has, or confidently calls one that was renamed, and the skill it is trusting looks authoritative.

Deriving the answer from the installed binary makes the version question disappear. There is no matrix of which skill version pairs with which CLI version, because the skill never claims anything version-specific. This is the same reason the project has no `engines` field between plugins and the CLI — see [the repository topology](/decisions/repo-topology.md) — arrived at from the opposite direction.

**It also makes the skills short.** Four files, none of them long, none of them duplicating a reference that already renders better from the tool. A skill's whole value is judgement — *when* to call a rune rather than re-scan the tree, *what* a scope error is really telling you — and judgement is what does not go stale.

## What it costs

**An agent must run a command before it can write code.** There is one more round trip than if the signatures were inline, and an agent that guesses instead of asking will guess from its training data, which is a worse source than either. The skills are written to push toward asking, but nothing enforces it.

**The skills cannot be reviewed against the CLI.** Because they state no API surface, no tool can check them for drift — there is nothing to compare. What can rot is the *command names* they use, and those are checkable: every subcommand the skills invoke exists in the shipped CLI, and that is worth re-checking whenever a command is renamed.

**It gives `crunes-skills` no knowledge bundle.** The repository's entire architecture is this one decision, which is why it is recorded here in the umbrella rather than in a bundle of its own — see [the knowledge base format](/decisions/knowledge-base-format.md).
