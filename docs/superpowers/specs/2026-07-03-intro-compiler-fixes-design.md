# intro-compiler.js documentation fixes — design

Date: 2026-07-03
Package: `crunes-cli` (`src/docs/intro-compiler.js`)

## Background

A cold-start onboarding session (no crunes Claude Code plugin/skill available, only
`crunes --help`, `crunes docs`, and a sibling project's runes as reference) produced a
feedback report (`crunes-feedback.md`) listing friction points hit while building a rune.
Every claim in that report was verified against `crunes-cli` source before writing this
spec — file/line citations are given per item below. All 9 items are confirmed real; none
were found to be misdiagnosed.

The intro (`crunes docs intro`, generated by `compileIntro()` in
`src/docs/intro-compiler.js`) is a single ~344-line function that pushes static markdown
lines into an array. There is no per-project dynamic content in the sections this spec
touches, so every fix is a static text edit to that file (plus one arguably-a-bug: item 2,
`helpSection()`/`helpText()` always rendering the whole rune's command tree with no way to
scope to the matched subcommand — this is existing, intentional behavior per source, but
still under-documented and is called out explicitly rather than papered over).

## Scope

In scope: `src/docs/intro-compiler.js` text-only changes (new paragraphs, corrected code
samples, one new subsection). No changes to parsing, help-rendering, or config-merging
behavior — those all work as designed; only their documentation is incomplete or shows a
convention that isn't the one real projects use.

Out of scope: adding `--help` interception to `crunes run` (item 1's option (a)) — the
report itself frames this as a design choice with two valid resolutions, and the source
shows it's already a deliberate rune-author responsibility (no accidental gap in `run.js`).
This spec takes option (b): document the behavior loudly, don't change it.

## Verified items and fixes

### 1. `crunes run <rune> --help` silently runs the rune (`src/rune/commands/run.js`)
Confirmed: `handler()` in `run.js` has no `--help`/`-h` special-casing anywhere in the
parsing or dispatch path. An unrecognized `--help` token is simply not consumed by
`args-parser.js` and the rune executes normally.
**Fix:** add a callout in "2. CLI Calling & Argument Conventions" (near the 3-tier
boundary section) stating plainly that `--help`/`-h` are not intercepted by `crunes run`,
and that rune authors must declare their own help option and check it in `run(args)`,
returning `rune.helpSection()`. Point to `crunes docs rune <key>` as the actual way to
preview a rune's CLI surface without executing it.

### 2. `rune.helpSection()`/`helpText()` always render the whole command tree
Confirmed in `src/rune/isolation/runner.js:1409-1411`: `getArgsSchema` returns the
top-level schema for the whole rune, and `formatHelp(schema, ...)` is called once, with no
use of `args.$commands`/`$command` to scope to a matched subcommand. `utils-bootstrap.js`
just exposes that one precomputed `__runeHelpText` string. There is no scoped variant.
**Fix:** state this explicitly wherever `helpSection()`/`helpText()` are introduced (the
Rune Exports API Reference section, generated from `lifecycle-api.json` — add a one-line
prose note immediately after that block since the API doc itself is TypeDoc-generated and
not hand-edited here): "always renders the full rune command tree, not scoped to the
matched subcommand — there is currently no way to get help for just one subcommand."

### 3. `ShellResult` uses `exitCode`/`ok`, not `code`
Confirmed in `src/rune/api/shell.js:7-12, 193-215`: the object has `exitCode` (number) and
`ok` (boolean, `exitCode === 0`). No `code` field exists anywhere.
**Fix:** the existing `shell` namespace recipe (`NAMESPACE_RECIPES.shell`, lines 126-139)
already uses `shell.exec` but discards the result shape entirely (just uses `stdout` as if
`exec` returns a string). Confirmed exact signature in `src/rune/api/shell.js:127`:
`exec(cmd, { throw: shouldThrow = true, trim = true, timeout = 30000, env, stdin, binary = false })`
— by default a non-zero exit **throws** a `ShellError` (carrying `stdout`/`stderr`/`exitCode`);
passing `{ throw: false }` instead returns `{ stdout, stderr, exitCode, ok }` for the caller
to check. Update the recipe to show the non-throwing check pattern (most common for a rune
that wants to report failure without an unhandled rejection):
```javascript
import { shell, section } from '@utils'

export async function run() {
  const result = await shell.exec('git status --short', { throw: false })
  if (!result.ok) {
    return section.create('git-status', { type: 'markdown', content: `Failed (exit ${result.exitCode}): ${result.stderr}` })
  }
  return section.create('git-status', { type: 'markdown', content: `\`\`\`\n${result.stdout}\n\`\`\`` })
}
```

### 4. Unmatched subcommand token falls through to `$rest`, not `$command`
Confirmed in `src/rune/api/args-parser.js:89-117`: the command-matching `while(true)` loop
only advances `commandsMatched` on an exact name match against `currentSchema.commands`;
any non-matching token simply breaks the loop. The token then flows through unchanged into
`args._` and, via `mapPositionals`, into `$rest` since it's not consumed by any declared
positional.
**Fix:** add one line immediately after the existing `$command`/`$commands`/`$rest` bullets
in "Custom Commands & Nested Parameters Mapping":
> An unrecognized subcommand does not populate `$command` — it falls through to the root
> (`$command === ''`) with the unmatched token in `$rest`. To report "unknown command,"
> check `args.$command === '' && args.$rest.length > 0`.

### 5. `env.read` pattern works without a `<source>::` prefix
Confirmed in `src/rune/permissions/permissions-env.js:3-19`: when the pattern body has no
`::`, `parseEnvPattern` treats the whole body as `keyPatterns` and defaults `sources` to
`['*']` (matches any source) — this is a fully supported, intentional form, not a
side-effect.
**Fix:** wherever `env.read` is documented (the `env` namespace section, generated per-ns
from `utils-api.json` — add a prose note similar to item 2's approach) state both forms
explicitly: `env.read:<source>::<key>` (scoped to one source) and the bare
`env.read:<key>` (matches the key from any source) are both valid; bare form is what most
existing projects use.

### 6. `vars`/`permissions` nesting — intro shows only one of two valid shapes
Confirmed in `src/core/config.js`: `mergeConfigs` step 2 (lines 19-33) merges `vars`
*nested inside* each `runes.<key>` entry; `validateConfig`'s second block (lines 76-93)
explicitly validates `runes[key].permissions` nested the same way. Separately,
`mergeConfigs` step 4 (lines 49-51) and `validateConfig`'s first block (lines 63-74) handle
a top-level `permissions` map keyed by rune name (today's documented shape). **Both shapes
are genuinely first-class, independently maintained code paths** — this isn't a legacy vs.
current situation, both are live.
**Fix (per user decision):** rewrite the "Sandbox Security & Permissions" example to nest
`vars` and `permissions` inside the `runes.<key>` entry as the primary/main shape:
```json
{
  "runes": {
    "my-rune": {
      "name": "My Rune",
      "description": "Does something useful",
      "path": ".crunes/runes/my-rune.js",
      "vars": { "api_url": "https://example.com" },
      "permissions": {
        "run": { "allow": ["fs.read:src/**", "fs.write:dist/**", "shell.run:git *"] }
      }
    }
  }
}
```
Add one sentence noting the alternative: a top-level `"permissions"` map keyed by rune name
(sibling of `"runes"`) is also supported and merges the same way — use whichever groups
better for the project. Also update the "run + repl both declared" example and the "Config
File Fields Reference" bullets to reflect nested placement as primary.

## Polish items

### 7. `crunes create` requires `--format` with no shown invocation example
Confirmed in `src/rune/commands/create.js:70-78`: in non-interactive mode (`--yes` or
non-TTY — the mode an agent session runs in), `format` is mandatory with no default and
errors immediately if missing/invalid (`VALID_FORMATS` = tree/markdown per line 75).
**Fix:** add a concrete `crunes create my-rune --format markdown --path
.crunes/runes/my-rune.js` (or similar) invocation right before the "Anatomy of a Rune" code
samples in section 1, so the first thing shown is how a rune file actually gets scaffolded,
not just its contents.

### 8. No example of a dynamic `args()` builder reading `vars`/`env` at schema-build time
The intro's only `args()` examples use static `.option()` chains (both in section 1's Run
mode example and the compiled Rune Exports API Reference). No existing recipe shows reading
config-time data to compute option choices/defaults (e.g., a `--profile <name>` whose valid
values come from `vars`).
**Fix:** extend the section 1 Run mode example (or add a short second example directly
after it) showing `args(builder)` reading `vars.read(...)` to build a profile option.
Confirmed exact API in `src/rune/api/vars.js`: `vars.read(key, fallback = undefined)` is
**synchronous** (not async) and `vars.has(key)` is also sync. Example:
```javascript
import { vars } from '@utils'

export function args(builder) {
  const profiles = vars.read('deploy_profiles', ['staging', 'production'])
  return builder.option('--profile <name>', `Deployment profile (${profiles.join('|')})`, profiles[0])
}
```

### 9. `.crunes/.gitignore` scaffold isn't mentioned in docs
Confirmed in `src/core/commands/init.js:7`: `crunes init` silently writes a `.gitignore`
covering `config.local.json`, `project.local.json`, `logs/`, `caches/`, `schemas/`,
`sqlite/`, `jobs/`.
**Fix:** add one sentence to the "Configuration Reference" intro (section 3, right after
the opening paragraph): "`crunes init` also scaffolds a `.crunes/.gitignore` covering
local-only files (`config.local.json`, `project.local.json`) and generated directories
(`logs/`, `caches/`, `schemas/`, `sqlite/`, `jobs/`) — only `config.json` and your rune
`.js` files need to be committed."

## Incidental observation (not fixing, flagging only)

`compileIntro()` currently takes no parameters, but its own test file
(`test/docs/intro-compiler.test.js`) calls it with `{ config, format, projectRoot,
configRoot }` — those arguments are silently ignored since the function signature doesn't
accept them. This doesn't affect the fixes in this spec (none of them need per-project
dynamic data), but it's a pre-existing inconsistency worth a maintainer's attention
separately.

## Non-goals / explicitly not changing

- Not adding `--help` interception to `crunes run` (see Scope).
- Not adding a scoped-help variant of `helpSection()` (documenting the limitation, not
  fixing it — that would be a behavior change, not a docs fix).
- Not changing which config shape (`permissions.<key>` sibling vs. nested) is "canonical"
  in code — both remain supported; only the docs' presentation order changes.
